# 原论文脚本条件下的显存实验统计与差异分析

报告日期：2026-10-07。数据来源：`/Users/maybe/paper-memory/`。本报告针对本次目录快照，不代表服务器当前运行状态。

## 1. 结论

已完成 56 个配置，其中每个配置保留作者五次运行循环。训练参数和控制流程沿用公开脚本；Amazon-Photo 的四层模型准确率已接近论文报告值。然而，全流程 allocator 峰值仍显著高于论文显存表，尚不能认定显存数值复现成功。

日志确认 GCN/SAGE 的高峰值集中在 `propagate()` 区间，区间结束时活跃分配已大幅下降。由此能确定本次峰值包含大量短暂分配，但不能据此断言论文采用了瞬时读数、手算张量大小或漏测峰值。论文未给出足够具体的测量接口和边界，测量口径及底层执行路径仍需核对。

## 3. 实验条件与统计定义

- 原脚本：BP 分别训练 1、2、3、4 层；SF 一次训练 4 层并保存各层前缀结果。
- 五次运行，seed=100，hidden=128，最多 1000 epoch，patience=100，val_every=2，lr=0.001。
- 实际环境：NVIDIA L40，PyTorch 1.13.1，PyG 2.2.0，CUDA 11.7；环境记录中 matmul TF32=False、cuDNN TF32=True。
- 新增 Python 执行边界跟踪与同步，保留原训练、评估、最终测试和五次运行生命周期；未主动清理分配器缓存。
- 准确率：五次原始结果的均值 ± 总体标准差（ddof=0）；BP perf 从比例转换为百分数，SF perf 已是百分数。
- 显存：整个配置进程（含五次运行）的 peak allocated，单位 MiB=2²⁰ 字节。它是五次运行流程中的最大值，不是五次峰值的均值，也不是单层独占内存。
- 进程峰值包含初始化、训练、内部评估、最终测试以及不同 run 切换阶段；旧 run 的引用和缓存按作者 main 原样管理，不能假定各次完全隔离。

## 7. 为什么与论文的绝对显存差异明显

### 7.1 已确认：本次统计捕获了巨大的临时峰值

本工具使用 max_memory_allocated()，捕获区间内瞬间达到、随后释放的高水位。若另一种方法只读取操作返回后的 memory_allocated()，同一调用就可能分别得到十几 GiB 和几十 MiB。这里的峰值不是累计分配量。日志已证明这个差距存在，但没有证明原论文使用的是后一种方法。

### 7.2 未对齐：论文没有充分公开统计边界

论文附录 B 描述统计参数、激活、梯度和 Adam 状态，但未给出足够具体的 API、重置时刻、采样频率和生命周期范围。本实验统计原五次运行进程的所有监控区间，还包括内部评估和测试。若论文采用张量分项统计、相对基线增量或不同时间窗口，就会出现明显差别；这些均为待验证假设，不应写成已确认事实。[论文实验设置](https://arxiv.org/html/2403.11004v1#A2)

### 7.3 待验证：底层执行路径和监控时序

propagate() 包含消息构造、聚合及可能的临时工作区；本工具未追踪到其内部 C++/CUDA 分配栈，不能把全部高峰值归因于边消息张量。稀疏/稠密输入路径、依赖构建、确定性算法设置和硬件都可能影响工作区。即使主版本相同也需进一步核对。逐行 GPU 同步也会改变执行时序，需要相同配置的无逐行插桩全程峰值对照。

### 7.4 不能用来单独解释差距的因素

- **缓存未清理**：本报告使用 peak allocated，空闲缓存不直接计入主指标；reserved 很高不能解释 allocated 曾达到的高峰值。
- **单位差异**：MB/MiB 换算约差 5%，远小于 GCN/SAGE 的数量级偏差。
- **训练不足**：本轮已恢复原 1000 epoch 上限和早停，Amazon 精度接近论文，高峰值仍存在。
- **仅仅换了显卡**：L40 与论文 H100 确实不同，但缺少受控证据，不能把几十至数百倍的数值差异直接归因于硬件。
