# SF 与 BP 深度扩展实验结果报告

报告日期：2026 年 10 月 5 日  
结果目录：`/Users/maybe/depth-main/`  
实验入口：`src/benchmark_depth_memory.py`

## 1. 主要结论

本次实验考察网络深度从 2 层增加到 64 层时，Single Forward（SF）与反向传播（BP）的 GPU 峰值显存变化。

在成功完成的 Amazon-Photo 实验中，SF-GCN 与 SF-SAGE 的峰值显存分别仅增长 **0.71%** 和 **0.25%**，支持“本次配置下 SF 的显存对深度变化不敏感”的判断。与 BP 的比较则取决于算子：

- **GCN：SF 的增长明显小于 BP。** SF 的显存增长斜率约为 BP 的 3.44%；在 64 层时，SF 的绝对峰值显存比 BP 低 12.28%。
- **GraphSAGE：SF 与 BP 均近乎不变。** SF 的绝对峰值显存与增长斜率略高于 BP，未体现相对内存优势。
- **GitHub：没有有效测量结果。** 全部配置因缺少预先要求的数据划分文件而失败，没有进入训练；不能据此判断内存需求或可扩展性。

因此，本轮结果不能概括为“SF 在所有数据集和算子上都比 BP 更省显存”，也不能证明总显存严格不随深度增长。

## 3. 显存测量口径

每个数据集、方法、算子、深度和划分组合均使用独立进程。主指标为 PyTorch CUDA allocator 记录的**全程 peak allocated**，单位为 MiB（1 MiB = 2²⁰ 字节）。

测量在 CPU 数据加载和 CPU 模型初始化之后、GPU 模型和数据传输之前开始，包含首次训练更新、Adam 状态初始化、后续训练以及训练器内部的评估和层间表示传递。最终测试使用 no_grad 单独记录窗口峰值，再与训练窗口取最大值，形成 whole_peak。各窗口切换时同步 GPU，不清理常驻数据。

本轮有效记录的 whole_peak 均由 training_peak 决定。这是完整流程的高水位，不是稳态单步内存，也不是 nvidia-smi 显示的整卡占用；CUDA context 和未经过 PyTorch allocator 的外部分配不在其统计范围内。原始 JSON 同时保存 peak reserved，本报告主表统一采用 allocated。

SF 和 BP 复用仓库各自的模型及训练流程。二者存在虚拟节点、局部损失、归一化和输出结构等差异，因此属于原实现之间的比较，不能把全部内存差异单独归因于逐层 detach。

## 4. Amazon-Photo 完整显存结果

下表为每个配置 5 个划分的均值。原报告中对应总体标准差均显示为 0.00 MiB；这不代表不同硬件、软件或训练协议下也没有波动。

| 层数 | GCN-SF（MiB） | GCN-BP（MiB） | SAGE-SF（MiB） | SAGE-BP（MiB） |
|---:|---:|---:|---:|---:|
| 2 | 2600.96 | 2448.10 | 13542.77 | 12958.27 |
| 4 | 2601.56 | 2465.45 | 13543.87 | 12959.28 |
| 8 | 2602.75 | 2500.15 | 13546.07 | 12961.29 |
| 16 | 2605.14 | 2569.56 | 13550.46 | 12965.30 |
| 32 | 2609.92 | 2708.39 | 13559.24 | 12973.33 |
| 64 | 2619.49 | 2986.03 | 13576.80 | 12989.39 |

增长比例定义为 `(M(64) / M(2) - 1) × 100%`；增长斜率使用全部六个深度点拟合 `M(L)=a+bL`，单位为 MiB/层。

| 模型 | 方法 | 2→64 层增加（MiB） | 相对增长 | 拟合斜率（MiB/层） |
|---|---|---:|---:|---:|
| GCN | SF | 18.53 | 0.71% | 0.299 |
| GCN | BP | 537.93 | 21.97% | 8.676 |
| SAGE | SF | 34.03 | 0.25% | 0.549 |
| SAGE | BP | 31.12 | 0.24% | 0.502 |

### 4.1 GCN：SF 的深度敏感性明显较低

GCN 的 SF 显存增长斜率为 BP 的约 3.44%，说明在本轮测量中，SF 随深度增加的额外显存需求远小于 BP。

但“增长较小”不等于“所有深度都更省”。在 2 层时，SF 比 BP 多占约 6.24%；在 16 层时仍略高于 BP。到已测量的 32 层和 64 层，SF 才分别比 BP 低 3.64% 和 12.28%。这些是离散测量点上的结果，不应把拟合交点当作实际测得的切换深度。

SF 局部训练无需保存完整跨层反向传播激活，与较低增长趋势相符；但当前数据没有做内存分项归因，不能将这一机制解释视为已经完成的消融验证。

### 4.2 GraphSAGE：两种方法都呈现高基线、低增长

SAGE 的 SF 和 BP 在 2→64 层的增长均小于 0.3%。SF 的斜率约为 BP 的 109.34%，且全深度范围内绝对峰值显存约高 4.51%～4.52%。因此，这组结果支持 SF 自身变化较小，但不支持 SF 相比 BP 更有优势。

两种方法都有约 13,000 MiB 的较高基线。一个待验证的解释是，输入处理或某个与总深度关联较弱的阶段主导了全程峰值，从而掩盖后续层的增长。仅凭目前的窗口级统计，无法确定峰值发生于哪个操作，也不能断言由第一层或特定聚合实现造成。

### 4.3 与设计阶段判据的对照

实验设计提出的工程判据为：2→64 层内 SF 峰值增长不超过 25%，且 SF 斜率不超过 BP 的 25%（BP 为正斜率时）。

- Amazon-Photo/GCN：两项均满足。
- Amazon-Photo/SAGE：满足自身增长阈值，但不满足相对 BP 的斜率阈值。
- GitHub：无有效结果，无法判断。

该判据用于描述本次结果，不是统计显著性检验，也不是算法复杂度定理。

## 5. GitHub 失败原因与补跑方式

全部 120 次 GitHub 运行均在划分文件检查阶段退出。例如：

```text
FileNotFoundError: Published dataset split required:
/home/chenh/forwardgnn/src/../datasplits/GitHub/node-5splits/train-node-index-split0.pt
```

split0～split4 的训练索引文件均被报告缺失。检查在遇到第一个缺失文件时退出，因此当前日志不能进一步证明验证和测试索引文件是否存在。需要确认五个划分的 train、val、test 文件均已放置到正确位置。

此错误由实验入口要求使用预先提供的作者划分触发，不是模型训练异常，也不是 CUDA OOM。补齐划分后，从服务器仓库根目录执行：

```bash
bash exp/nodeclass/nodeclass-depth-memory.sh \
  --gpu 0 --runs 5 --datasets GitHub \
  --output results/depth-github
```

输出目录必须新建或为空。Amazon-Photo 已完成的结果无需为补齐 GitHub 而重新计算。

## 6. 精度与结论边界

本轮预算用于内存扫描，不能用于宣称最终收敛精度。为避免只报告内存而忽略模型质量，列出浅层与最深层的测试准确率均值：

| 模型 | 方法 | 2 层准确率 | 64 层准确率 |
|---|---|---:|---:|
| GCN | SF | 47.39% | 63.92% |
| GCN | BP | 29.05% | 25.37% |
| SAGE | SF | 43.82% | 35.80% |
| SAGE | BP | 26.17% | 25.37% |

SF 每层训练 20 epoch，而 BP 整体训练 20 epoch，两者不是等计算预算。以上数值仅说明本轮运行产生了什么结果，不构成公平的最终精度或效率比较。

此外，本次实验只有一个成功的数据集、固定隐藏宽度 128，以及一种硬件和软件环境。全程 allocator 峰值的统计口径也不能直接等同于原论文的显存表。对更广泛适用性的判断需要补齐 GitHub、增加宽度对照，并在更充分的训练预算下复核。

## 7. 后续建议

1. 补齐 GitHub 的五个数据划分，完成第二个数据集的配对结果。
2. 在 SAGE 上增加独立诊断实验，分别记录初始化、第一层、后续层训练和评估的峰值，定位高基线来源；诊断结果与本轮原始协议分开报告。
3. 在固定深度集合上补充隐藏宽度 64、256 的实验，判断当前趋势是否依赖宽度。
4. 对代表性深度使用更充分的训练及验证早停预算，同时报告精度，避免把低显存直接解释成有用的深层模型。

## 8. 可引用的结果描述

> 在 Amazon-Photo 节点分类任务上，固定隐藏宽度为 128，并将网络深度从 2 层扩展至 64 层时，SF-GCN 与 SF-SAGE 的全程 CUDA 峰值已分配显存分别增长 0.71% 和 0.25%。其中，GCN 的 SF 显存增长斜率仅为 BP 的 3.44%，且在 64 层时峰值显存较 BP 降低 12.28%；GraphSAGE 的 SF 和 BP 均呈现近乎恒定的峰值，SF 未体现相对优势。这些结果表明，SF 在本次 Amazon-Photo 配置下具有较低的深度内存敏感性，但其相对于 BP 的优势依赖于算子和测量场景。GitHub 实验因缺少数据划分文件未产生有效结果。
